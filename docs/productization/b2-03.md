## 1. What the frozen chain allows (checked, not assumed)

Read from `chain/x/compute/keeper.go` during implementation:

```text
MsgBondWorker requires amount > 0            -> "invalid bond amount" for zero,
                                               so bond/register is always >= 1 uprsm
the bonded network key cannot be replaced    -> "bonded network key cannot be replaced"
QueryWorkerResponse has no profile field     -> the GPU/profile capability is NOT on chain;
                                               capability refresh is a gateway announcement
proto3 JSON omits zero values                -> a fresh worker's worker-query answers {}
```

Those four facts shape the whole design: `join` always submits a real bond
top-up, a re-registration is a top-up carrying the key, capability changes
are recorded locally as `gateway_announcement_pending` (network layer, not
the chain), and the frozen-surface check must accept `{}` from a fresh
account.

## 2. Join sequence (order matters)

```text
1. chain identity        validate chain-id BEFORE anything else — never probe
                         or announce into the wrong chain (unit-tested order)
2. capability gate       CAPABILITY_UNSUPPORTED refuses the join unless
                         --allow-unsupported REASON is given; the reason is
                         recorded in the state file
3. frozen surface        `query compute worker --worker <addr>` must answer
                         (the frozen protocol has no version query; the served
                         query surface + chain-id are the enforceable checks —
                         recorded honestly, not papered over)
4. balance gate          needs (bond target - bonded) >= 1 uprsm; a shortfall
                         is an actionable error (amount, address, how to fund)
5. bond/register tx      one MsgBondWorker with amount + network key + proof,
                         signed from a temporary 0700 keyring that is shredded
                         immediately afterwards (see section 4)
6. verify on chain       query again and require the chain to show OUR key
                         before reporting success; a mismatch is a hard error
7. state file            chain_id, address, node_id, bonded/reserved, capability,
                         override reason, tx hash, gateway_announcement_pending
```

`heartbeat` re-validates the chain (and that the endpoint still serves the
same chain), re-probes the capability, flags a capability change or a lost
chain-side registration, and updates the state file — bounded by
`--iterations` for tests and CI use.

## 4. Bounded key exposure (deliberate, documented)

Transactions need the chain account key. The canonical secret stays in the
encrypted keystore (B2-01); per transaction the key is imported into a
temporary 0700 keyring directory that is overwritten and deleted
immediately afterwards (`_temporary_keyring` + `_shred_tree`, tested). A
headless worker host has no OS keyring, and a persistent copy would be
worse; a native signer is the long-term fix and belongs with B5.

## 5. Fixes and deviations recorded

1. **B1-03 tool bug found and fixed here**: `netconfig provision` did not
   import the account key into the provisioned node home, so a provisioned
   node could not sign any transaction (found by the smoke's funding step).
   Fixed in `chain/tools/netconfig/verify.go`; the netconfig test suite is
   green. This is a maintenance fix to a B1-03 deliverable, outside B2-03's
   `worker/**` allowed list — recorded rather than hidden.
2. **Autocli query shape**: `query compute worker` takes `--worker <addr>`
   as a flag, not positionally; a regression test now pins the command
   shape.
3. **Join order and error handling**: the chain identity check moved ahead
   of the GPU probe, and `JoinError` is now handled by the CLI as a clean
   refusal (exit 1) instead of a traceback.
4. **B2-01g correction**: the frozen chain cannot replace a bonded network
   key, so protocol-key rotation requires a fresh account + bond. The
   worker README's recovery section now says exactly that.
