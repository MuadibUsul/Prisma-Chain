## 1. The crash-point map

Every crash point classifies to exactly one action, with no state transition
that could double-submit or lose funds:

```text
crash point                        journal phase     action            outcome
before accept                      discovered        retry             nothing submitted
mid accept (chain already ours)    accepting         reconcile_chain   -> accepted (no tx)
mid accept (chain has other)       accepting         abandon           -> abandoned
mid accept (chain shows nothing)   accepting         reconcile_chain   retry accept (guarded)
accept failed, task still open     accept_failed     retry             retry accept
accept failed, task taken          accept_failed     abandon           -> abandoned
after accept / mid execution       accepted/executing resume           re-execute (deterministic)
after execution, before commit     executed          resume            build+sign (guard active)
after commit, before DA quorum     submitted         reconcile_chain   verify inclusion, then DA
after commit, chain disagrees      submitted         abandon           -> abandoned
before DA quorum                   da_pending        resume            upload only missing providers
after DA quorum                    da_quorum         terminal          chain finalizes
already terminal/abandoned         terminal/abandoned terminal         sticky
task finalized/fraud/refunded      any               terminal          nothing to add
```

## 2. Why it cannot double-submit or lose funds

- **Recovery submits no transactions.** It only reads the chain and moves
  journal phases; transactions stay in the normal pipeline, whose guards
  already exist (journal-first accept idempotency, B2-04; duplicate-commit
  refusal keyed by commit id, B2-07). Recovery is therefore safe to run twice.
- **The chain wins.** A task the chain assigned to another worker, or that is
  finalized/fraud/refunded, is abandoned or terminated — never resumed into
  an inconsistent view (`abandoned` is sticky, so a later run cannot revive
  it accidentally).
- **Minimal rework.** `providers_to_upload` re-uploads only to providers
  without a verified attestation (the journal carries `da_verified`).

## 3. Evidence

`pytest -q worker/tests` — **132 passed, 1 skipped** (20 new):

```text
13 parametrized crash points (the table above) classify exactly as documented
mid-accept reconciliation records `accepted` WITHOUT any transaction (fake chain
    asserts accept_task is never called)
an assignment belonging to another worker is abandoned and stays abandoned
    (a later run with a corrected chain view still returns terminal)
finalized tasks terminate every phase
recovery is idempotent: two consecutive runs produce identical actions
DA resume uploads only the missing providers
summary counts match the decisions
```

The tests run `recover_task`/`recover_all` against a fake chain that **fails
the test if any transaction is attempted** — the "no double-submit" property
is asserted structurally, not by inspection.

## 5. Carried into the B2 product gate

The gate (directive: join → accept → execute → CommitV3 → DA quorum →
finalize → VWR on a clean GPU machine) needs real SM86/SM89 hardware; the
fault-injection at each crash point against a **live** worker process (kill
-9 and restart) is part of that run and is not claimed here. The
classification logic, the journal contract and the no-transaction property
are complete and tested.
