# B2-02 — GPU probe / capability report

```text
Task ID     B2-02
Status      DONE (2026-10-05)
Branch      product/testnet-alpha
Module      worker/prisma_worker/gpu.py + `prisma-worker gpu probe`
Goal        report the local GPU honestly and refuse unproven hardware
```

## 1. Rule: no silent fallback

The worker executes the frozen canonical graph with the
`TRUE_FUSED_MMA_A13W10` backend, which is bit-exact only on the compute
capabilities proven in Phase F:

```text
8.6  NVIDIA A40                    (F.5B.2 bit-exact evidence)
8.9  NVIDIA RTX 2000 Ada Generation (F.5B.2 bit-exact evidence)
```

Anything else is reported as `CAPABILITY_UNSUPPORTED` with the reason and
an empty supported-profile list. There is no CPU path, no silent
degradation, and the probe never guesses: a missing `nvidia-smi` or a
driver that cannot report a compute capability is an explicit error, not an
assumed value.

## 2. Output

```text
status / gpu / vram / driver / cuda runtime / backend / supported /
reason / profiles / notes
```

`status` is `CAPABILITY_SUPPORTED` or `CAPABILITY_UNSUPPORTED`;
`--json` gives the machine-readable form. The CLI uses distinct exit
codes so the join flow can branch without parsing text: **0** supported,
**2** unsupported, **1** probe error.

## 3. Verification

**Unit tests (7) + CLI regression test, all green** (`pytest -q worker/tests`:
29 passed, 1 skipped overall): A40 and RTX 2000 Ada are supported; an
SM75 host is unsupported with the reason naming the proven targets; a
missing `nvidia-smi` is an explicit error mentioning the absence of any
CPU fallback; malformed/`N/A` compute-capability rows are refused; a
multi-GPU host reports the first device plus a note instead of silently
picking one; the report serialises and formats.

**Real probe on the development host (this is the honest case):**

```text
$ python -m prisma_worker gpu probe
status            CAPABILITY_UNSUPPORTED
gpu               NVIDIA GeForce RTX 2060 SUPER (compute capability 7.5)
vram              8.0 GiB
driver            616.92
cuda runtime      not detected
backend           TRUE_FUSED_MMA_A13W10
supported         no
reason            compute capability 7.5 is not a proven target (8.6, 8.9 only); the frozen
                  kernels cannot execute bit-exactly here and no CPU fallback exists
note              torch 2.14.1+cpu is a CPU-only build; the worker needs the CUDA build
exit=2
```

The development machine is below the proven floor, so **every GPU-backed
gate in B2 (join/execute/product gate) must run on SM86/SM89 hardware**
(rented GPU). That is an external dependency recorded here, not something
the code can work around.

**Bug found by the real run.** The first `gpu probe` invocation crashed
with `AttributeError: 'Namespace' object has no attribute 'keystore'` —
`main()` assumed every subcommand carries an identity flag. Fixed
(keystore path handling is now conditional) and guarded by a CLI
regression test that exercises the supported, unsupported and probe-error
exit paths.

## 4. Definition of Done check

```text
probe reports GPU model / CC / VRAM / driver / CUDA runtime      yes (section 3)
backend compatibility + supported profiles are explicit          yes — proven targets only
unsupported hardware is CAPABILITY_UNSUPPORTED, exit code 2      yes (real run, SM75)
no silent CPU fallback                                           yes — missing GPU is an explicit
                                                                 error; the report names it
```

## 5. Carried into later tasks

1. B2-03 (`join`) consumes this report and must refuse to join with
   `CAPABILITY_UNSUPPORTED` unless an operator explicitly overrides with a
   recorded reason (to be decided there; the current default is refuse).
2. The worker image (B1-01 lineage) must ship the CUDA-enabled torch build;
   a CPU-only torch is detected and named rather than silently used.
3. The frozen kernel builds target SM86/SM89 only (`gpu/f5b2/f5b2_ext.py`);
   adding another architecture is a versioned GPU-backend change, not a
   config toggle.
