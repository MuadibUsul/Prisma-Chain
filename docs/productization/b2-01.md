## 1. Identity model

| key | algorithm | job | public form |
|---|---|---|---|
| protocol key | ed25519 | capability announcements, receipts, network-key binding proof | `node_id` = sha256(pubkey); base64/hex public key |
| chain account | secp256k1 | funded, bonded account that submits transactions | bech32 `prsm1…` |

The two are deliberately separate: the protocol key is what the network
verifies, the chain account is what the chain charges and bonds.

## 2. Sub-step map

| item | implementation |
|---|---|
| B2-01a generate protocol key | `WorkerIdentity.generate()` — ed25519, local, 32-byte seed |
| B2-01b import protocol key | `identity import --protocol-key-hex HEX` (with or without `0x`), account key via `--account-key-hex`/`--account-key-file` |
| B2-01c chain account | secp256k1 derivation → RIPEMD160(SHA256(compressed)) → bech32 `prsm1…`; `identity show` prints the public record without the passphrase |
| B2-01d encrypted storage | keystore v1: scrypt(n=2^15,r=8,p=1) + AES-GCM, version as AAD, atomic write, 0600 |
| B2-01e permissions | refuse to load a group/world-readable keystore on POSIX (Windows relies on profile ACLs — recorded, not assumed) |
| B2-01f no secrets in logs | two-layer redaction (`«redacted»` for registered secrets including exception tracebacks, `«redacted-hex»` for any 64+ hex run); `redact.install()` for daemons |
| B2-01g key rotation | `identity rotate` prints retired + new public records and the announce-before-retire procedure (README) |
| B2-01h recovery behaviour | lost passphrase → explicit `UnrecoverableKeystoreError` ("no recovery path"); lost file → documented re-import; compromised → rotate |

## 3. Verification

**Tests — 21 passed, 1 skipped** (skip is the POSIX-permissions case on
Windows, which is itself the documented platform difference):

```text
$ cd worker && python -m pytest tests/ -q
21 passed, 1 skipped in 1.64s
```

Coverage highlights:

- **address vector from the chain's own tooling**:
  `prismad keys import-hex vec 1111…11` → `prismad keys show vec -a` =
  `prsm1l3e9pgs3mmwuwrh95fecme0s0qtn28806jn3dq` and pubkey
  `A081W9y3zAr3KO88zrlhXZBoS7Wyyl+FmrDwtwQHWHGq` — asserted in
  `test_account_address_matches_chain_tooling`, so this package cannot drift
  from the node's address format silently;
- protocol signature + network-key binding proof are byte-identical to
  `prisma_network.core.Identity` for the same seed (single source of truth
  for the wire format);
- keystore: roundtrip, secrets absent from the file, wrong passphrase →
  unrecoverable, tampered ciphertext → rejected, weakened KDF → refused,
  no `.tmp` leftovers, rotation replaces the identity;
- logs: registered secrets vanish from message/args/f-strings/tracebacks,
  unregistered 64-hex keys are still redacted, short values are not
  over-redacted, the CLI prints no secret and writes no plaintext.

**RIPEMD-160 fallback.** `cryptography` 50 removed `hashes.RIPEMD160` (and
OpenSSL 3 does not always expose `ripemd160` through `hashlib`), so the
package prefers `hashlib` and falls back to an in-tree pure-Python
implementation, checked against the four published vectors:

```text
ripemd160("") = 9c1185a5c5e9fc54612808977ee8f548b2258d31
ripemd160("abc") = 8eb208f7e05d987a9b044a8e98c6b087f15a0bfc
ripemd160("message digest") = 5d0689ef49d2fae572b881b123a85ffa21595f36
ripemd160("a"×10^6) = 52783243c1697bdbe16d37f97f68f08325dc1528
```

**CLI demo (real run):**

```text
$ PRISMA_WORKER_PASSPHRASE=… python -m prisma_worker identity init --keystore … --json
{"node_id": "65d5fb34…", "account_address": "prsm18n8zw0sah6gdjmmfedslj4qpfjhk6rfn4lmmad", …}

→ same public record
```

## 5. Open items for later B2 tasks

1. **Funding/bonding** the chain account happens in B2-03 (`join`): this
   task only derives and stores the address.
2. **Network-key binding announcement**: the proof is implemented
   (`network_key_proof_hex`) and matches the gateway's verification path;
   the announcement transaction itself belongs to B2-03.
3. The daemon (B2-04+) must call `redact.install()` and
   `register_secret(...)` before logging — recorded in the README as the
   contract for future code.
4. Rotation needs a chain-side "announce new key before retiring the old"
   flow; today the CLI documents the procedure and prints both records.
