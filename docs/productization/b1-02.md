## 1. Topology

```text
                        public internet
                              │  only the proxy listens here
                              ▼
              ┌───────────────────────────────┐
              │ prismad rpc-proxy             │  method allow-list (403)
              │ read-only policy by default   │  per-IP rate limit (429)
              │ no keys, signs nothing        │  body cap (413), timeout (504)
              │ /healthz  /metrics            │  websockets refused (501)
              └──────────────┬────────────────┘
                             │ http://127.0.0.1:26657 (node RPC never public)
              ┌──────────────▼────────────────┐      ┌───────────────────────┐
              │ sentry / rpc-public           │◀────▶│ other sentries, seeds │
              │ full node — no key in the     │ p2p  └───────────────────────┘
              │ genesis validator set         │
              └──────────────┬────────────────┘
                             │ p2p on a private link only
              ┌──────────────▼────────────────┐
              │ validator-private             │  consensus key exists ONLY here
              │ rpc bound to localhost        │  persistent peers = its sentries
              └───────────────────────────────┘
```

A validator never accepts public connections: the sentry speaks to the open
network on its behalf, and only the proxy faces the public. `prismad
rpc-proxy` holds no key material and reads no node config, so it is safe to
run on the same host as (or in front of) a public edge.

## 2. Implementation map

| roadmap item | implementation |
|---|---|
| B1-02a RPC-only node mode | `netconfig profile --role rpc-public` produces a non-validator full-node config; such a node never appears in the genesis validator set, so it holds no network signing key (only its inert local `priv_validator_key.json`, which signs nothing when the node is not a validator) |
| B1-02b validator peer segregation | `validator-private` profile binds p2p to the private interface (default localhost) with `pex = false` and persistent peers limited to sentries; `sentry` is the only role with a public p2p laddr and `pex = true` |
| B1-02c request size limits | `http.MaxBytesReader` at the proxy; **413** with an explicit JSON reason (default 1 MiB cap) |
| B1-02d rate limiting | per-IP token bucket (`--rate`, `--burst`); **429** + `Retry-After` |
| B1-02e query timeouts | bounded upstream client (`--upstream-timeout`, default 15 s); **504** with the bound in the message |
| B1-02f metrics | Prometheus-style counters at `/metrics`: totals by status class, rate-limited, method-denied, size-denied, websocket-refused, timeouts, upstream errors, upstream latency |
| B1-02g health endpoint | `/healthz` (its own path, never the full RPC surface): upstream `/status` check with a 3 s bound → 200/503 |
| B1-02h sentry topology docs | section 1 + the concrete config example in section 3 |
| B1-02i abuse/load smoke | `deploy/rpc_smoke.py`, recorded results `docs/productization/b1-02-rpc-smoke.json` (section 4) |

Profiles are generated by `netconfig profile --role …`, derived from the
real SDK config template (`prismad init` in a scratch home) with the role's
listen/peer policy applied; roles that expose RPC also emit a concrete
`rpc-proxy.json`. Nothing in a profile embeds key material.

## 3. Concrete example (sentry)

```text
$ netconfig profile --role sentry --out profile-sentry --moniker sentry-1 \
      --external-address 203.0.113.30:26656 --peers abc123…@10.0.0.5:26656

config.toml:   moniker            = "sentry-1"
               [p2p] laddr        = "tcp://0.0.0.0:26656"      (public, intentional)
               external_address   = "203.0.113.30:26656"
               persistent_peers   = "abc123…@10.0.0.5:26656"
               pex                = true                        (written as a TOML bool)
               [rpc] laddr        = "tcp://127.0.0.1:26657"     (never public)
rpc-proxy.json: listen 0.0.0.0:8545, upstream tcp://127.0.0.1:26657,
                policy read-only, rate 20/s, burst 40, body cap 1 MiB, upstream 15 s
```

Boot verification: a node provisioned from a bundle and given this
generated `config.toml`/`app.toml` starts and finalizes blocks
(`prisma-profilesmoke-1`, heights 4→5, `finalizing commit` in the log).
During this verification a real bug was found and fixed: `pex` was first
written as a quoted string, which CometBFT cannot parse — booleans are now
written as raw TOML values (`setTomlRawInSection`).

## 4. Abuse/load smoke — 10/10 PASS

```text
$ python deploy/rpc_smoke.py --prismad <bin> --netconfig <bin>
  PASS  normal GET /status: expected=200 observed=200
  PASS  allowed JSON-RPC method: expected=200 observed=200
  PASS  write method denied: expected=403 observed=403
  PASS  heavy path denied through proxy: expected=403 observed=403 (node itself serves it: 200)
  PASS  oversize body rejected: expected=413 observed=413
  PASS  websocket refused: expected=501 observed=501
  PASS  flood rate-limited: expected=>=1 request answered 429 observed=33/40 with 429, 7 with 200
  PASS  health endpoint: expected=200 observed=200
  PASS  metrics exposed: expected=200 + counters observed=200
  PASS  bounded upstream timeout: expected=504 observed=504 (upstream hangs 5s, proxy timeout 1s)

rpc smoke: 10 passed, 0 failed -> docs/productization/b1-02-rpc-smoke.json
```

The smoke brings up a real single-validator node from a generated bundle,
fronts it with the real proxy, and records every observation (including
the proof that the node itself still serves the blocked heavy path, so the
denial genuinely happens at the proxy boundary). The script fails the run
on any unexpected result — findings are recorded, not softened.

Unit tests: `chain/rpcproxy` covers allow/deny, batch requests,
unparseable bodies, size cap, per-IP rate limit with a controlled clock,
bounded timeout, health endpoint, websocket refusal and metrics counters.

## 5. Known limitations (recorded, not hidden)

1. **No websockets** through the proxy (501 by design): clients needing the
   event stream must be pointed at a dedicated endpoint with its own limits.
2. **Per-IP keying uses the connection address**; the proxy does not trust
   `X-Forwarded-For`. Behind a load balancer, rate limits apply per LB
   address until a trusted-proxy mode is added (deliberate: trusting the
   header without a trust boundary is a bypass).
3. **No TLS termination** here: run the proxy behind a TLS terminator or
   the platform's ingress for real deployments.
4. **Metrics are process-local** counters (no histogram buckets), enough
   for M4/M5; richer observability can build on the same counters.
5. Mempool/write/unsafe methods are denied by the read-only preset: a public
   RPC must not expose transaction submission by default (a faucet or API
   submits through their own paths).
