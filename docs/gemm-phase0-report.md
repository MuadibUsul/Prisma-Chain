## Definition of Done checklist (§36)

   Python, 3 vector cases, byte-identical).
2. Normal worker reaches FINALIZED — **PASS** (optimistic path, receipt
   `optimistic_unchallenged`).
3. A corrupted output tile is discovered by the challenger — **PASS**
   (library tests, CLI and network E2E).
4. Dispute creates a trace for one tile only — **PASS** (trace exists only
   inside `NewGEMMDispute` after a validated ChallengeOpen; nothing else
   builds traces).
5. Bisection localizes one K-step — **PASS** (e.g. R=512: 9 rounds).

   8x8x8; verified against an independent oracle in tests).

## Benchmark ladder (CPU reference, Windows x64)

Full data: `docs/gemm-benchmark-results.json` (generated by
`prisma-gemm benchmark --sizes 128,256,512,1024,2048,4096 --out ...`).

| Shape | Reference GEMM | Matrix commitment | Output commitment | Normal-path overhead | Challenge detection | On-demand trace | Bisection | Arbitration | Challenge cost / full recompute |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 128³ | 2 ms | 1 ms | 1 ms | 0.60x | 1 ms | 4,352 B | 4 rounds | 0.5 ms | 0.91x |
| 256³ | 12 ms | 2 ms | 2 ms | 0.33x | 12 ms | 8,448 B | 5 rounds | 2.0 ms | 1.17x |
| 512³ | 91 ms | 8 ms | 7 ms | 0.16x | 95 ms | 16,640 B | 6 rounds | 8.3 ms | 1.13x |
| 1024³ | 701 ms | 31 ms | 31 ms | 0.09x | 713 ms | 33,024 B | 7 rounds | 31.8 ms | 1.06x |
| 2048³ | 5,579 ms | 121 ms | 110 ms | 0.04x | 5,544 ms | 65,792 B | 8 rounds | 124.7 ms | 1.02x |
| 4096³ | 44,683 ms | 474 ms | 427 ms | 0.02x | 46,194 ms | 131,328 B | 9 rounds | 486.2 ms | 1.05x |

Reading the numbers:

- Normal-path overhead (commitment work relative to the GEMM itself) falls
  from 0.60x at 128³ to 0.02x at 4096³: commitment cost is linear in the
  output size while the GEMM is cubic, so the optimistic path adds ~2% at
  the top of the ladder on this CPU.
- On-demand trace size grows linearly in R (`(R+1) x 256` bytes per party)
  and stays in the kilobytes to ~131 KB, versus terabytes for a full-task
  trace commitment at 4096³.
- Bisection rounds grow as ceil(log2(R)) and the round messages are
  256-byte states with short proofs; the measured bisection time is below
  1 ms up to R=512.
- Challenge cost against full recomputation converges to ~1.02–1.05x at
  large shapes: a dispute costs roughly one extra recomputation, paid only
  when fraud is plausible. The arbiter's own share is one 512-MAC step.
- Peak heap at 4096³ was 6.5 GB (A, B, C and tile structures of the
  reference path); disk usage is the Go build cache plus the JSON artifacts;
  the E2E moved under 1 MB of network traffic per dispute at dev scale.

GPU numbers (native GEMM time, GPU cross-check) are NOT TESTED here; the
GPU adapter records them on a CUDA node via `deploy/runpod_gemm/`.

## Known limitations

- The two-node Python E2E trusts the transport for signatures: ResultCommit
  and ChallengeOpen signatures are exercised in the Go library and CLI, but
  the HTTP service does not re-verify Ed25519 signatures yet (Phase D
  concerns; the chain module will require them).
- The worker service keeps one task in memory and regenerates matrices from
  a seed; real tasks will fetch inputs from `data_ref` storage.
- Full-verification challenges are allowed in v0.1.1, so challenger cost
  scales like the GEMM itself; spot-check sampling is future work.
- `micro-step` arbitration assumes the low state is common: this is
  guaranteed by bisection but not independently re-proven by the arbiter.
- GPU evidence, GPU bit-exactness and multi-GPU scaling are unmeasured here
  (no CUDA device); the code refuses to claim a GPU gate without one.

## Next protocol blocker

The Phase D chain integration is the next hard step: GEMM task admission,
ResultCommit and ChallengeOpen transactions, the dispute state machine with
bonds and deadlines, and VWR-based settlement must be added to the existing
compute module without disturbing bounded-VM tasks, then exercised through
the devnet before any public testnet claim.

## Final protocol question (§37)

> Can a large-scale INT8 GEMM result submitted by an untrusted GPU worker
> be located and adjudicated through optimistic challenge without letting
> the arbiter recompute the full task?

**PARTIAL.**

- YES for everything that does not require two real GPU machines: two
  independent implementations agree bit-for-bit; fraud in one output tile
  is detected by a challenger with no access to worker intermediates; the
  dispute locks traces for that tile only, bisects in O(log2 R) rounds,
  and the arbiter decides with exactly 512 canonical MACs after verifying
  input tiles against the committed matrix roots; a losing worker gets no
  receipt and a false challenger loses; all of this passes in the Go test
  suite, through the CLI, and over a real two-process HTTP E2E, including
  at 4096³ where the normal path stays trace-free (131 KB on-demand trace
  vs terabytes).
- NOT TESTED for the last mile: the same flow on two independent GPU nodes
  with a bit-exact INT8->INT32 CUDA kernel and published GPU benchmark
  numbers. That evidence is exactly what the new Verifiable GEMM gate in
  `docs/delivery.md` item 7 requires before this PARTIAL becomes YES.
